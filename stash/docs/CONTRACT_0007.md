# Contract 0007 · free pipeline

Binding for the two builders (WORKER/BACKEND and APP). SQL source of truth:
`supabase/migrations/0007_free_pipeline.sql`. Types: `lib/supabase/types.ts` (already updated,
generated by `scripts/gen-types.py`). If something here is wrong or missing, tell the orchestrator;
do not change the migration or the types yourself.

Goal: $0 per month, no card, one thing for the owner to do (paste a Gemini key in Supabase Vault),
fast first paint of a save, and a save always ends `ready`.

## 1. Architecture

```
phone (Next.js PWA) ──insert saves/asks──► Postgres (schema stash)
        ▲   │                                   │ trigger → pg_net POST <stash_worker_url>/run
        │   │ functions.invoke                  │           header x-stash-worker-token (Vault)
        │   ▼                                   ▼
        │  Edge Functions                 Worker (Vercel Python function, 300 s)
        │   stash-embed (JWT)                   │ every Supabase call goes through
        │   stash-recovery                      ▼
        │   stash-worker-proxy ◄────── x-stash-worker-token ── has the service key natively
        └── Realtime (saves, asks, …)           │ PostgREST (schema stash), RPCs, Storage signing, embeddings
```

- No service role key outside Supabase. The worker holds **no secret at all**: its only env var is
  `SUPABASE_URL` (not secret). It gets the token from the wake-up request, keeps it in memory for
  that invocation, and gets API keys from `worker_config()` through the proxy.
- No R2, no Voyage, no ffmpeg, no Cloud Run.

## 3. Schema changes (0007)

### saves: new columns (all written by the worker only; `guard_save_columns` resets them for the phone)

| column | type | values |
|---|---|---|
| `process_step` | text, default `queued` | `queued` → `fetching` → `watching` → `reading` → `filing` → `ready` |
| `video_state` | text, default `none` | `none` \| `stored` \| `blocked` \| `too_big` \| `evicted` |
| `playback` | text, default `link` | `video` \| `embed` \| `link` \| `none` |
| `embed_url` | text null | iframe URL, checked by the database (see §7) |
| `video_bytes` | bigint null | size of the stored MP4 |
| `ai_state` | text, default `pending` | `pending` \| `done` \| `no_key` \| `retry` \| `not_owner` \| `over_budget` \| `failed` |

Constraint `saves_video_consistent`: `video_state = 'stored'` ⇔ `video_path is not null`;
`playback = 'video'` needs `stored`; `playback = 'embed'` needs `embed_url`. So the worker sets
`video_path`, `video_bytes`, `video_state`, `playback` **in one PATCH**.

`status` keeps its enum. `request_reprocess(save_id)` still works; the guard resets `process_step`
to `queued` when the phone moves status back to `queued`.

`ai_state = 'retry'`: the save is `ready` but its AI steps did not run because the provider was busy
(HTTP 429 / 503 / 529) or the worker's run was nearly over. The sweep re-queues
`reprocess {"mode": "insights"}` for it (10 minutes apart, at most 8 tries a day). The app shows
"The summary is on its way"; nothing for the owner to do.

### jobs: what a phone may do

The phone inserts `grade` jobs itself and `reprocess` through `request_reprocess()`. A trigger
(`guard_job_insert`, fired only for statements the phone runs itself: `current_user` is
`authenticated`) refuses every other type, forces `state = queued`, `attempts = 0`,
`run_after = now()`, keeps only `card_id` / `audio_path` / `text` in a grade payload, empties a
reprocess payload, and silently skips a `reprocess` while an `ingest` or full `reprocess` for the
same save is still queued or running. Phones can read their jobs but not update or delete them.
Jobs made by SECURITY DEFINER triggers and functions (ingest, export, ask, synthesize, galaxy,
backup, the sweep) are untouched: inside those, `current_user` is the function's owner.

`process_step` meaning (the app shows one line per step):

| step | worker is doing | app copy (suggestion) |
|---|---|---|
| `queued` | waiting for the worker | Waiting |
| `fetching` | metadata, then the video download | Getting it |
| `watching` | transcription / vision | Watching |
| `reading` | insights (key idea, takeaways, cards) | Reading |
| `filing` | embedding, Space suggestion, upload bookkeeping | Filing |
| `ready` | done (also set on `failed` / `dead_link` ends) | (card shows) |

## 4. Edge Functions (WORKER/BACKEND builder; Deno, `supabase/functions/<name>/index.ts`)

All three read `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` from the function
environment (injected by Supabase; nobody handles them). All RPCs use `.schema('stash')`. Errors are
`{"error": "<code>"}` with the status given. All answer `OPTIONS` with CORS headers
(`Access-Control-Allow-Origin: *`, headers `authorization, x-client-info, apikey, content-type`).

### 4.1 `stash-worker-proxy` (verify_jwt = false)

Every request: header `x-stash-worker-token`. Missing or `worker_token_ok` false → `401 unauthorized`
(the result may be cached in memory for 60 s, keyed by the token's SHA-256). Paths are relative to
`/functions/v1/stash-worker-proxy`.

| route | request | response |
|---|---|---|
| `POST /config` | `{}` | `worker_config()` plus `{"supabase_url": …, "anon_key": …}` |
| `GET\|POST\|PATCH\|DELETE /rest/<target>?<query>` | body and query passed through to `${SUPABASE_URL}/rest/v1/<target>` with the service key; the proxy forces `Accept-Profile: stash` and `Content-Profile: stash` and forwards only `Prefer`, `Range`, `Content-Type` | upstream status + body |
| `POST /storage/sign-upload` | `{"bucket", "path"}` | `{"url", "token", "path"}` (absolute signed upload URL, upsert allowed). The worker then `PUT`s the bytes to `url` with `Content-Type` and `x-upsert: true`, straight to Storage |
| `POST /storage/sign-download` | `{"bucket", "path", "expires_in"?: 600}` | `{"url"}` |
| `POST /storage/remove` | `{"bucket", "paths": string[] (≤ 100)}` | `{"removed": n}` |
| `POST /embed` | `{"input": string[] (≤ 16; each cut to 2000 chars)}` | `{"embeddings": number[][], "model": "gte-small", "dims": 384}` |

Allowlist (anything else → `403 forbidden`):

- `/rest/<target>`: `<target>` is one of the tables `saves, insights, transcripts, embeddings, places,
  states, cards, reviews, syntheses, reminders, jobs, exports, usage, settings, spaces, media_trash,
  galaxy_points, galaxy_clusters, galaxy_layouts, asks, highlights, backups, daily_queues, imports`,
  or `rpc/claim_jobs`, `rpc/ask_context`, `rpc/evict_videos`. Never `config`, `rate_limits`,
  `recovery`, `push_subscriptions`, other RPCs, or another schema.
- `PATCH` and `DELETE` need at least one filter in the query string (else `400 filter_required`).
- Storage: bucket ∈ `stash-video, stash-thumbs, stash-exports, stash-voice`; path matches
  `^[0-9a-f]{8}-[0-9a-f-]{27}/[A-Za-z0-9._/-]{1,200}$` and contains no `..`.
- No route reaches `/auth/v1`. Request bodies over 1 MB → `413`. Videos never pass through.

Embeddings (shared with stash-embed in `supabase/functions/_shared/embed.ts`):
`new Supabase.ai.Session('gte-small')`, `run(text, {mean_pool: true, normalize: true})`, 384 numbers.

### 4.2 `stash-embed` (verify_jwt = true)

`POST` with the phone's session (`supabase.functions.invoke('stash-embed', {body})`).

- Request `{"input": string | string[]}` (≤ 4 strings, each cut to 1000 chars).
- Rate limit: `rate_limit_take('u:' + sub, 'embed', 60, 60)`, then all callers together
  `rate_limit_take('all', 'embed_all', 3000, 60)`; over either → `429 rate_limited`.
- Response `{"embeddings": number[][], "model": "gte-small", "dims": 384}`.

### 4.3 `stash-recovery` (verify_jwt = false; the function checks the JWT itself for `create`)

Derivation (only in this function; the app never derives anything):

- Code: 20 characters of Crockford base32 (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`, 100 random bits from
  `crypto.getRandomValues`), shown as `XXXXX-XXXXX-XXXXX-XXXXX`.
- `norm(code)`: uppercase, drop everything that is not a letter or digit, `O→0`, `I→1`, `L→1`; must
  then be 20 alphabet characters, else `400 invalid_code`.
- `lookup` = first 32 hex chars of `SHA-256("stash-recovery/v1/id/" + norm)`.
- `password` = base64url of `HMAC-SHA-256(key = norm, message = "stash-recovery/v1/password")`.
- `email` = `<lookup>@recovery.stash.invalid` (domain in one constant; restore reads the stored email,
  so it can change later).

`POST {"action": "create"}` with `Authorization: Bearer <access token of the current device>`:

1. `auth.getUser(token)` → `uid`, else `401 unauthorized`.
2. `rate_limit_take('u:' + uid, 'recovery_create', 5, 86400)`, else `429 rate_limited`.
3. Generate the code; `auth.admin.updateUserById(uid, {email, password, email_confirm: true})`.
4. `recovery_set(uid, lookup)`.
5. Setting a password ends every session the user had, this device's included. So the function signs
   in right away with the new email and password (anon client, `signInWithPassword`).
6. `200 {"code": "XXXXX-XXXXX-XXXXX-XXXXX", "created_at": "<iso>", "access_token", "refresh_token",
   "expires_at"}` (the three session fields are `null` when the sign-in failed). The app calls
   `supabase.auth.setSession(…)` **before** it shows the code; if that fails it still shows the code and
   says this phone needs it to get back in. Shown once; calling again rotates: the old code stops
   working and the owner's **other phones are signed out** (they enter the new code). The user id and
   all data stay the same.

`POST {"action": "restore", "code": "…"}` (no session needed):

1. `rate_limit_take('ip:' + sha256(ip).slice(0,32), 'recovery_restore', 10, 3600)`, where `ip` is
   `cf-connecting-ip` when present, else the **last** `x-forwarded-for` hop (earlier hops are whatever
   the caller sent); then all callers together `rate_limit_take('all', 'recovery_restore_all', 600, 3600)`;
   over either → `429 rate_limited`.
2. `norm`, `lookup`; `recovery_find(lookup)` → null → `404 not_found`.
3. `auth.admin.getUserById(uid)` → email; anon client `signInWithPassword({email, password})`;
   failure → `404 not_found`.
4. `200 {"access_token", "refresh_token", "expires_at", "user_id"}`. The app calls
   `supabase.auth.setSession(…)`, clears its local caches (outbox must be empty or flushed first) and reloads.

Stored: in `auth.users` the synthetic email and the password hash; in `stash.recovery` the lookup id
and two dates. The code itself is stored nowhere. `cleanup_anonymous_users` skips users with a
`recovery` row (and they are no longer anonymous).

## 5. Worker (WORKER/BACKEND builder; Vercel project, root `stash/worker`, Hobby)

- Entry `api/index.py` (FastAPI/ASGI), `vercel.json`: rewrite `/(.*)` → `/api/index`,
  `functions.api/index.py.maxDuration = 300`, `"fluid": true`. Env: `SUPABASE_URL` only. Proxy base =
  `${SUPABASE_URL}/functions/v1/stash-worker-proxy`.
- Bundle under 250 MB: no ffmpeg, no boto3. numpy only if the Galaxy job cannot do without
  (prefer pure Python PCA + k-means on ≤ 2 000 × 384). Keep reportlab / python-docx / python-pptx.
- `/tmp` is the only writable directory (500 MB).

Endpoints:

| | |
|---|---|
| `GET /` | `{"ok": true, "supabase_url_set": bool}`. No secrets, no feature probing |
| `POST /run` | header `x-stash-worker-token`. Missing or shorter than 32 → `401`. Calls proxy `/config`; proxy `401` → `401`. Then runs the queue and answers `{"done", "failed", "requeued", "trashed"}` |

Run loop: `claim_jobs(1)` through the proxy, process, repeat until the queue is empty,
`run_budget_seconds` have passed or fewer than 90 s are left before the deadline
(`worker_max_seconds` − 15 s); then delete up to 50 `media_trash` rows (`/storage/remove`, then
delete the rows). Everything slow reads the same deadline: no video download with under 60 s left
(yt-dlp is cancelled from its progress hook with under 25 s), no transcription with under 60 s, no
insights call with under 40 s, and provider calls and the Storage `PUT` use timeouts cut to the time
left. A step skipped for time leaves `ai_state = 'retry'`; the save still ends `ready`. The token and the keys live in local variables only, never logged, never written
to disk. Concurrent invocations are fine (`claim_jobs` skips locked rows).

### Jobs

| type | row | payload | result |
|---|---|---|---|
| `ingest` | `save_id` | `{}` | full pipeline below |
| `reprocess` | `save_id` | `{}` = full pipeline; `{"mode": "insights"}` = AI steps only, status stays `ready`, no download | |
| `synthesize` | `space_id` set, or null with payload `{"tag": "<lowercase tag>"}` | | `syntheses` row; for a tag: `space_id` null, `tag` set, sources = the user's ready saves whose `insights.tags` contain it (case-insensitive) |

| `backup` | `user_id` | `{}` | see below |
| `export`, `grade`, `galaxy` | unchanged | | Galaxy now reads 384-dim vectors |

Every job: refuse when the row it names belongs to another user than `job.user_id` (existing
`owner_mismatch` rule; applies to `ask_id` too). AI and video storage only for `job.user_id` in
`worker_config().owner_ids`.

### Ingest pipeline

1. `saves`: `status = processing`, `process_step = fetching`.
2. **Metadata first (target < 5 s), one PATCH**: `title`, `creator_handle`, `caption`, `duration_s`,
   `thumb_path`, `embed_url`, provisional `playback`.
   - TikTok: `https://www.tiktok.com/oembed?url=…`. YouTube: `https://www.youtube.com/oembed?url=…&format=json`.
     Instagram: `og:` tags of the page (often blocked: then skip, not an error). Web: `og:` tags.
   - Thumbnail: download the platform's image (≤ 2 MB, jpeg/png/webp), upload to
     `stash-thumbs/<uid>/<save_id>.jpg` through a signed upload URL. No frame extraction.
   - 404/410 from both oEmbed and the page → `status = dead_link`, `process_step = ready`, stop.
3. **Video** (owner only; Instagram and TikTok; YouTube only when `youtube_download = on`): yt-dlp, one
   progressive MP4, no merge (`best[ext=mp4][vcodec!=?none][acodec!=?none]`, sorted `vcodec:h264,
   res:720`; the `?` keeps a direct MP4 whose codecs are not announced), refuse over
   `max_video_seconds` or `video_max_mb` (`too_big`). yt-dlp is only ever given an `https` address whose
   host is the platform's own (exact or a subdomain; YouTube as the watch URL rebuilt from the video
   id), with `allowed_extractors` set to that platform's extractor, so its generic extractor never runs. Then `evict_videos(bytes)`, sign-upload to
   `stash-video/<uid>/<save_id>.mp4`, `PUT`, one PATCH `{video_path, video_bytes, video_state: 'stored', playback: 'video'}`.
   Any download failure → `video_state = 'blocked'`, keep going.
4. `process_step = watching`: transcript → `transcripts`.
   YouTube: captions with yt-dlp (`skip_download`, subtitles / automatic captions). Stored MP4: send the
   file to the transcription provider (Gemini: file upload; Groq: the MP4 itself, ≤ 25 MB). Screenshot:
   vision on the image. Web: readable article text (title + main text, ≤ 20 000 chars) goes into
   `transcripts.full_text` with `segments = []`.
5. `process_step = reading`: insights from whatever exists (transcript, caption, title, article text;
   caption alone is enough) → `insights`, `places`, `cards`, up to 3 `highlights` (`source = 'ai'`).
   No usable provider → `ai_state = 'no_key'` and skip (the sweep re-queues it later). Not an owner →
   `not_owner`. Budget reached → `over_budget`. Provider busy (429 / 503 / 529) or no time left in this
   run → `retry` (the sweep re-queues it). Any other provider error after retries → `failed` (the save
   is still ready).
6. `process_step = filing`: embed `title + key idea + caption + transcript[:1500]` through proxy
   `/embed` (works with no AI key; skip only when there is no text at all) → upsert `embeddings`
   `{save_id, user_id, vector: "[…]", model: "gte-small"}`; `usage` rows (`provider` set).
7. One PATCH: `status = ready`, `process_step = ready`, `processed_at`, `ai_state`, `error = null`.

Only an unexpected exception retries the job (3 attempts) and can end in `status = failed`
(`process_step = ready`); the sweep does the same for a job whose worker died four times. A blocked
download, a missing key or an AI error never fails a save.

### AI provider abstraction (`worker/stash_worker/ai/` or equivalent)

One interface, three implementations chosen from `config.ai_provider` / `transcribe_provider` and the
keys present: `understand(text, spaces) → insights`, `vision(image) → text + insights`,
`transcribe(file) → segments`, `grade(card, answer)`, `synthesize(saves)`, `ask(question, context)`,
`brief(...)` (exports). Gemini through its REST API with `httpx` (no heavy SDK); keep the existing
Claude and Groq code paths behind the same interface. Model ids only from `config`.

### Ask job

1. `asks.status = running`. 2. Embed the question (`/embed`). 3. `rpc/ask_context(user_id, question,
embedding, 8)`. 4. No rows → `ready` with answer "Nothing in your saves about that yet." and no
citations. 5. Otherwise the fast model answers from the context only, returning JSON
`{"answer": string, "cited": [save_id…]}`; keep only ids that were in the context. 6. PATCH
`{status: 'ready', answer, cited_save_ids}`; no provider → `{status: 'failed', error: 'no_ai'}`;
provider busy (429 / 503 / 529) → the ask goes back to `queued` and the job is retried a minute or
two later (3 attempts); other failure → `failed` with a short error. `usage.kind = 'ask'`.

### Backup job

Read the user's rows of `spaces, saves, insights, transcripts, places, states, cards, reviews,
syntheses, reminders, highlights, asks, settings` through the proxy (paged, 1 000 rows), write
`{"version": 1, "created_at", "user_id", "tables": {name: rows[]}}` as JSON to
`stash-exports/<uid>/backups/<YYYY-MM-DD>.json`, insert a `backups` row (`upsert on user_id,path`),
then delete the user's `backups` rows beyond the newest `backup_keep` (the delete trigger queues the
files for removal).

### Keep-alive

`.github/workflows/stash-keepalive.yml`: twice a week, `curl` the public RPC
`POST ${SUPABASE_URL}/rest/v1/rpc/vapid_public_key` with the publishable key and
`Content-Profile: stash` (repository variables, not secrets). Nothing in the database.

## 7. Playback decision table (worker writes, app reads)

`embed_url` (the database refuses anything else):

| platform | `embed_url` |
|---|---|
| tiktok | `https://www.tiktok.com/player/v1/<numeric video id>` (resolve `vm.tiktok.com` short links first; the id is in the oEmbed answer `embed_product_id` or the final URL) |
| instagram | `https://www.instagram.com/<p\|reel\|tv>/<shortcode>/embed` |
| youtube | `https://www.youtube-nocookie.com/embed/<video id>` |
| web, screenshot | null |

| case | `video_state` | `playback` |
|---|---|---|
| MP4 stored | `stored` | `video` |
| download refused / failed | `blocked` | `embed` if `embed_url` else `link` |
| too long or too large | `too_big` | `embed` if `embed_url` else `link` |
| not an owner, or YouTube with `youtube_download = off` | `none` | `embed` if `embed_url` else `link` |
| evicted by retention (set by SQL) | `evicted` | `embed` if `embed_url` else `link` |
| web article | `none` | `link` |
| screenshot | `none` | `none` |

## 9. Deploy order (orchestrator)

## 10. Acceptance checks

- Worker: with no AI key a TikTok link ends `ready` with title, thumbnail, `playback` set and
  `ai_state = 'no_key'`; after the key is added the sweep's `reprocess {"mode":"insights"}` fills
  `insights` without re-downloading.
- Worker: title and thumbnail are written before the download starts.
- Proxy: wrong token → 401; `/rest/config`, `/rest/recovery`, `rpc/worker_config`, a `public` table,
  bucket `avatars`, path with `..` → 403; `DELETE /rest/saves` without a filter → 400.
- Embed: 384 numbers, unit length; the 61st call in a minute → 429.
- Recovery: create → code, and the device that made it is still signed in afterwards (same `user_id`,
  its saves still load); restore on a clean browser profile → same `user_id` and saves; old code
  fails after rotate; 11th restore attempt in an hour from one IP → 429.
- App: `tsc`, `eslint`, `vitest`, `next build` pass; no reference to `/api/search`, `/api/media`,
  `R2_`, `VOYAGE_` remains.
- SQL attack checks (run by the architect on a local Postgres, all passed): another device cannot
  read asks, highlights, backups, recovery rows or video objects; cannot call `worker_config`,
  `worker_token_ok`, `owner_ids`, `ask_context`, `evict_videos`, `rate_limit_take`, `recovery_*`,
  `cfg`, `vault_text`; cannot forge answers, playback columns or a highlight on someone else's save;
  a wrong, short or prefix token is refused; a phone cannot queue any job but `grade` / `reprocess`,
  cannot set a job's state or attempts, cannot update or delete jobs, and cannot reset the ask, save
  or job limits by deleting rows.
